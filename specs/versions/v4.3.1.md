# v4.3.1 — Word Hunt invite open from browser (Android)

**Status:** Complete.

## Scope

### Player-facing

- **HTTPS invite links open Gridly on Android** — tapping a shared Word Hunt invite in Chrome (or after opening the link in a real browser) shows the branded landing page; **Open in Gridly** and the auto-redirect use a correct Android `intent://` URL so the installed APK receives `gridly://games/word-hunt/play?mode=custom&invite=…` with the invite id intact
- **Landing page without JavaScript** — on Android, the primary button’s `href` is the intent URL in the initial HTML (not only after inline script runs), so a tap still works if script is blocked or slow
- **Legacy corrupted links** — invites opened from very old landing pages that delivered `amp;invite` instead of `invite` are repaired in `app/+native-intent.tsx` when the app handles the deep link

### Engineering

- `supabase/functions/_shared/deepLink.ts` — intent URL includes `action=android.intent.action.VIEW` and `BROWSABLE` / `DEFAULT` categories
- `resolve-invite` — `detectClientPlatform` from `User-Agent`; **302 redirect** to `intent://` (Android) or `gridly://` (iOS) for phone browsers so the HTML interstitial is not shown; chat preview crawlers and `?fallback=1` still receive the branded HTML page
- `app.json` — explicit `gridly://games` and legacy `gridly://game` intent filters (plus scheme-only fallback)
- `app/+native-intent.tsx` — `redirectSystemPath` normalizes legacy query strings

## Acceptance criteria

### Server (no new APK)

- [x] Deployed `resolve-invite` returns `302` with `Location: intent://…` for a normal Android Chrome `User-Agent` (no `?fallback=1`)
- [x] `?fallback=1` and WhatsApp preview fetchers receive `200` branded HTML
- [x] `?fallback=1` suppresses auto-redirect (`data-autoredirect="0"`)
- [x] Unit tests cover intent URL shape and landing script navigation

### App (existing or new APK)

- [x] With **any** installed build that already registers the `gridly` scheme (`com.gridly.app`), opening the invite after **only** redeploying `resolve-invite` is sufficient for end-to-end testing
- [x] A **new** APK build picks up refined `intentFilters` in `app.json`; required for production confidence, not for verifying the server landing fix alone
- [x] **Expo Go** does not represent production invite open (`exp://`, not `com.gridly.app`); use an existing APK, a **development build** with `gridly` scheme, or `npx uri-scheme open` against a dev build

## Out of scope

## Notes

**Minimum test path:** `supabase functions deploy resolve-invite`, then open a fresh invite link in **Chrome on the phone** with the **current APK** installed. Rebuild the APK when shipping the `app.json` intent-filter and `+native-intent` changes to stores or testers.
